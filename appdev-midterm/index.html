Application Development and Emerging Technologies

Lesson 1: SDLC, Modern Architecture, MVC & DevOps

01
Lifecycle Phases

Software Development Life Cycle (SDLC) Phases

What is the SDLC?
The Software Development Life Cycle (SDLC) is a shared map of how a product moves from an initial idea to running software.
1
Planning
Define the goal, constraints, people, and success criteria before writing code.
Establishes project scope, timelines, resources, and feasibility at the very start.
2
Analysis
Gather and clarify requirements: what the system must do and for whom.
Translates user and business needs into clear functional and non-functional specifications.
3
Design
Choose architecture, data models, interfaces, and how system parts will collaborate.
Produces technical blueprints, database schemas, and UI wireframes before implementation begins.
4
Implementation
Build working software from the design, in small verifiable pieces when possible.
Developers write, compile, and integrate the actual source code for the application.
5
Testing
Check that the product meets requirements and is safe to release.
Verifies functionality, performance, and security while catching defects before users see them.
6
Deployment
Release the application to users in a controlled, repeatable way.
Packages and publishes the validated build to production servers or app stores.
7
Maintenance
Fix defects, adapt to change, and keep the system healthy after launch.
Covers ongoing bug patches, performance tuning, security updates, and new feature enhancements.
02
Lifecycle Models

Comparing SDLC Models: Waterfall, Agile & Spiral

1. Waterfall
A
When to Use
Requirements are stable, the domain is well understood, and a linear plan is realistic.
Best for fixed-scope projects with predictable rules.
B
Waterfall Flow
Phases run once, in order.
Each phase finishes completely before the next starts; change late in the project is expensive.
2. Agile
A
When to Use
You need working software often and expect requirements to evolve.
Ideal for fast-moving products where customer needs change over time.
B
Agile Flow
Phases repeat in short cycles.
Short cycles repeat analysis, design, build, and test, while user feedback steers the next increment.
3. Spiral
A
When to Use
Larger, riskier efforts where prototypes and risk reviews drive each cycle.
Used when technical or safety risks must be evaluated before committing to full builds.
B
Spiral Flow
Risk-driven iterative loops.
Each loop plans, assesses risk, builds a prototype or increment, and evaluates before the next loop.
03
Application Architecture

Modern Applications & Client-Server Layers

Core Architecture
A modern web application is a client that talks to a server over HTTP. The server owns business rules and data, while the client owns the user experience.
Three-Tier Layer Explorer
1
Client Layer
The browser or front-end app users interact with directly (such as an Angular or React web app).
It renders screens, collects user inputs or answers, and calls backend APIs over HTTP.
2
Server Layer
The backend application and API (such as an ASP.NET Core Web API) that processes requests.
It enforces business rules, validates inputs, handles security/authentication, and communicates with the database.
3
Database Layer
The persistent data storage system (such as SQL Server) that stores and retrieves records.
It keeps application entities, user accounts, and transactions safe and organized on disk.
Modern Application Concepts
1
SPA (Single-Page Application)
The client stays loaded in the browser and updates the page without a full reload.
Only the needed data is fetched in the background, making navigation feel instant and fluid.
2
API (Application Programming Interface)
JSON over HTTP lets many different clients (web, mobile, desktop) share one server.
The backend exposes clean endpoints that any authorized front-end device can call.
3
Separation of Concerns
UI, business rules, and data storage are kept in separate layers rather than mixed into one file.
This modular structure makes code easier to read, test, debug, and maintain over time.
04
Architectural Pattern

Model-View-Controller (MVC) Architecture

Purpose of MVC
MVC separates data (Model), presentation (View), and request handling (Controller) so each part can change with less chaos.
1. Model
M
Data and Rules
Represents domain entities, business logic, and data state (e.g., users, questions, orders).
Defines what data the application holds and how it is stored in the database.
2. View
V
Presentation / UI
The visual interface shown to the user (screens, forms, buttons, templates).
Displays data from the system and captures user actions like clicking Submit.
3. Controller
C
Request Handler
Receives a request, uses models, and returns a result.
Acts as the traffic coordinator between incoming HTTP requests and backend Models.
How an MVC Request Flows End-to-End
1
Step 1 — View
The user interacts with the View (for example, clicking a Submit button in the front-end app).
2
Step 2 — Controller
The Controller receives the HTTP request (such as POST /api/submit) and invokes the appropriate business logic.
3
Step 3 — Model & Database
The Model is validated and saved in the database (such as SQL Server), and a response is returned.
05
CI/CD & Automation

DevOps and the 5-Stage CI/CD Pipeline

What is DevOps?
A way of working where development and operations share one path from code change to production, with fast feedback and minimal manual effort.
The 5 Steps of a CI/CD Pipeline
1
Commit
A developer records a change in version control (Git).
Pushing that commit automatically triggers the start of the CI/CD pipeline.
2
Build
Automation compiles the backend API and front-end app so everyone uses the exact same recipe.
Catches missing dependencies or compilation errors immediately on a clean build server.
3
Test
Automated checks catch regressions before a person has to click through every screen manually.
Runs unit, integration, and end-to-end tests automatically on every build.
4
Deploy
Automation releases the verified build to staging or production environments in a repeatable way.
Eliminates risky manual file copying and ensures consistent, fast software delivery.
5
Monitor
Logs, system health, and user feedback flow back so the next commit is better informed.
Tracks live performance, uptime, and error rates in production to guide future improvements.
Key DevOps Automation Practices
1
Continuous Integration (CI)
Every commit is built and tested automatically when pushed to the shared repository.
Prevents "integration hell" by catching broken code or failing tests within minutes.
2
Infrastructure as Code (IaC)
Servers and environments are described in versioned files, not manual "tribal knowledge".
Allows teams to spin up identical test and production servers automatically from code scripts.
3
Feedback Loops
Test results, live monitoring, and user metrics inform the team’s very next change.
Continuous telemetry connects daily engineering decisions directly to real-world system behavior.

Lesson 2: C# Programming & .NET Fundamentals

01
Language & Runtime

Introduction to C#, .NET & Compilation

1
What is C#?
A modern, object-oriented and type-safe (statically typed) programming language from Microsoft.
Object-oriented means modeling data and behavior with classes; type-safe means the compiler checks data types (such as int count = 3;) before the program runs.
2
.NET Platform & Source Files (.cs)
C# source code files end in .cs and run on the .NET platform.
Edited and debugged using Visual Studio or Visual Studio Code, and built from the terminal using the dotnet CLI.
3
Compilation (Build Phase)
Translates .cs source files into Intermediate Language (IL) and checks for syntax or type errors before running.
If a semicolon or type is wrong, compilation fails immediately and the program never starts.
4
Runtime (Execution Phase)
Executes the compiled program on the .NET runtime after the build succeeds.
Runs your instructions line by line and interacts with the user or operating system.
5
dotnet CLI Commands
Terminal commands used to create and run a C# console project.
dotnet new console -n HelloLab cd HelloLab dotnet run
6
Top-Level Statements (Modern Entry Point)
Lets you write executable statements directly at the top of Program.cs without wrapping them in a class.
Console.WriteLine("Hello, World!");
7
Classic Program Class & Main Method
The traditional C# entry point where execution begins inside static void Main().
class Program { static void Main() { Console.WriteLine("Hello, World!"); } }
02
Data & Expressions

Data Types, Variables, Constants & Operators

Core Data Types & Constants
1
int (Whole Number Type)
Stores whole integers without decimals (positive, negative, or zero).
int age = 18;
2
double (Floating-Point Decimal Type)
Stores numbers with fractional decimal parts.
double gpa = 3.5;
3
string (Text Type)
Stores a sequence of characters enclosed in double quotes " ".
string name = "Alex";
4
bool (Boolean Logic Type)
Stores a truth value that can only be true or false.
bool isEnrolled = true;
5
const (Constant Declaration)
Declares a fixed value that cannot be changed after it is initialized.
Attempting to reassign a const variable later in the program causes a compile error.
const int MaxScore = 100;
Operators in C#
1
Arithmetic Operators ( +, -, *, / )
Perform standard mathematical addition, subtraction, multiplication, and division.
int total = (10 + 5) * 2; // 30
2
Modulo / Remainder Operator ( % )
Returns the remainder left over after integer division.
Commonly used to check if a number is even (n % 2 == 0) or odd.
int n = 10; Console.WriteLine(n % 2 == 0); // Prints True
3
Comparison Operators ( ==, !=, <, >, <=, >= )
Compare two values and evaluate to a bool (true or false).
bool isPassing = grade >= 75;
4
Logical AND Operator ( && )
Evaluates to true only when both conditions are true.
bool canEnter = hasTicket && isOpen;
5
Logical OR Operator ( || )
Evaluates to true when at least one condition is true.
bool getsDiscount = isStudent || isSenior;
6
Logical NOT Operator ( ! )
Inverts a boolean value (turns true into false, and false into true).
bool isOffline = !isOnline;
03
Control Flow & Methods

Decisions (if / else), Loops & Methods

1
if Statement
Evaluates a bool condition inside parentheses ( ) and runs its block if the condition is true.
int grade = 92; if (grade >= 90) { Console.WriteLine("A"); }
2
else if & else Branches
Tests additional conditions in order when previous if conditions are false, with else as the fallback.
Only the first matching branch executes; all remaining branches are skipped.
if (grade >= 90) { Console.WriteLine("A"); } else if (grade >= 75) { Console.WriteLine("B"); } else { Console.WriteLine("Keep practicing"); }
3
for Loop (Count-Controlled Loop)
Repeats a block of statements a known number of times using an initializer, condition, and step increment.
for (int i = 0; i < 5; i++) { Console.WriteLine(i); }
4
while Loop (Condition-Controlled Loop)
Repeats a block of statements as long as its boolean condition remains true.
int count = 3; while (count > 0) { count--; }
5
Methods (Reusable Code Blocks)
A named block of code that accepts parameters, performs a task, and optionally returns a value.
int Add(int a, int b) { return a + b; }
6
Local Scope
Variables declared inside a method or block exist only inside that block’s curly braces { }.
They are invisible and inaccessible outside the method where they were created.
04
Syntax Rules

Basic Syntax: Delimiters, Comments, Keywords & Naming

1
Semicolon ( ; ) — Statement Terminator
Marks the end of an executable C# statement (such as variable declarations, assignments, and method calls).
Omitting a required semicolon causes a compile error.
int count = 3; Console.WriteLine(count);
2
Curly Braces ( { } ) — Code Blocks
Group multiple statements together into a single scope block for classes, methods, conditionals, and loops.
if (count > 0) { Console.WriteLine("Positive"); }
3
Parentheses ( ( ) ) — Conditions & Method Arguments
Hold boolean conditions in if/while statements and parameters or arguments in method calls.
Console.WriteLine("Pass arguments inside parentheses");
4
Square Brackets ( [ ] ) — Array Declarations & Indexing
Used to declare array types and access elements at a specific index.
int[] nums = { 10, 20 }; Console.WriteLine(nums[0]); // Access index 0
5
Single-Line Comment ( // )
Tells the compiler to ignore everything from // to the end of that line.
// This single-line note is for human readers int retries = 3;
6
Multi-Line Comment ( /* ... */ )
Wraps notes that span across multiple lines between /* and */.
/* Everything inside this block is ignored by the C# compiler */
7
Reserved Keywords
Built-in words like int, class, return, if, while, and static that have special meaning to the compiler.
Reserved keywords cannot be used as ordinary variable or method names.
8
camelCase Naming Convention
Starts with a lowercase letter and capitalizes each subsequent word; used for local variables and method parameters.
int itemCount = 5; string studentName = "Alex";
9
PascalCase Naming Convention
Capitalizes the first letter of every word; used for classes, methods, and properties.
class ScoreCalculator { void CalculateTotal() { } }
05
Console Apps & Collections

Basic Applications: Console I/O, Parsing & Collections

1
Console.WriteLine() & Console.Write()
Prints text output to the terminal window (WriteLine adds a newline at the end; Write stays on the same line).
Console.Write("Enter your name: "); Console.WriteLine("Welcome!");
2
Console.ReadLine() — Reading User Input
Waits for the user to type a line of text and returns it as a string?.
string? name = Console.ReadLine();
3
String Interpolation ( $"..." )
Prefixes a string with $ so you can embed variables directly inside curly braces { }.
Console.WriteLine($"Hello, {name}");
4
int.Parse() & int.TryParse() — Converting Text to Numbers
Converts a text string (such as "25") into an integer (int) so you can perform math on user input.
int.Parse throws an error if the text is not a valid number, whereas int.TryParse safely returns false without crashing.
int age = int.Parse("25"); bool isValid = int.TryParse(input, out int safeScore);
5
Integer Division Truncation ( int / int )
Dividing two int values discards any decimal remainder rather than rounding.
Use double when your calculation needs to preserve decimals.
int truncated = 7 / 2; // Evaluates to 3 double exact = 7.0 / 2; // Evaluates to 3.5
6
Arrays ( int[] ) — Fixed-Size Zero-Indexed Collection
Stores a fixed number of elements of the same type where the first item is always at index 0.
int[] scores = { 88, 91, 74 }; Console.WriteLine(scores[0]); // Prints 88 (first item) Console.WriteLine(scores.Length); // Prints 3 (total items)
7
List<T> — Dynamic Resizable Collection
A generic collection that grows and shrinks dynamically as you add or remove items.
List<int> grades = new List<int> { 88, 91 }; grades.Add(95);

Lesson 3: Git Version Control & Repository Commands

01
Git Architecture

The Four Core Git Areas

How Git Tracks Changes
Files move from your Working Tree → into the Staging Area (Index) via git add → into the HEAD Snapshot (Commit Graph) via git commit.
1
Working Tree (Working Directory)
Your active project folder where you create, edit, or delete files before staging them.
Changes made here are unstaged (or untracked for brand-new files) until you run git add.
2
Staging Area (Index)
The middle preparation zone that holds changes queued for the next commit.
Lets you carefully select which modified files to group together into a single clean snapshot.
3
HEAD Snapshot
A pointer to the latest committed snapshot on your currently active branch.
Whenever you create a new commit or switch branches, HEAD updates to point to that current state.
4
Commit Graph
The historical chain of parent-to-child commit snapshots across all branches in the repository.
Allows teams to inspect project history, branch off safely, and merge features back together.
02
Basic Snapshot Workflow

Repository Setup, Staging & History Commands

1
git init
Creates a new Git repository in the current folder.
HEAD points at main with no commits yet.
git init
2
git status
Shows the current branch, staged changes, unstaged edits, and untracked files.
The most frequently used inspection command to check the state of your working tree and index.
git status
3
git add <file> | git add .
Copies working-tree files into the index (staging area).
Stage a specific file by name or use . to stage all modified and untracked files in the directory.
git add readme.txt git add .
4
git commit -m "message"
Records a permanent snapshot of the staging index and moves the current branch forward.
Always write a clear, concise message describing what changed in the snapshot.
git commit -m "Add initial readme file"
5
git log [--oneline]
Walks parent commits backward starting from HEAD.
Adding --oneline prints a compact one-line summary (commit hash + message) for each commit.
git log git log --oneline
03
Branching & Merging

Branching, Switching & Merging Commands

1
git branch [name]
Lists existing branches (with no arguments) or creates a new branch pointing at HEAD.
Creating a branch with git branch does not switch to it automatically.
git branch git branch feature-login
2
git switch [-c] <branch>
Moves HEAD to a target branch and updates the working tree.
Passing the -c flag creates a new branch and switches to it immediately in a single command.
git switch main git switch -c feature-login
3
git checkout [-b] <branch>
Classic command for switching or creating branches.
Passing -b creates a new branch and switches to it, equivalent to git switch -c.
git checkout main git checkout -b feature-login
4
git merge <branch>
Joins another branch’s history into the current branch (via fast-forward or 3-way merge).
Always switch to the receiving branch (such as main) before running git merge.
git switch main git merge feature-login
04
Diffs, Undo & Removal

Inspecting Differences, Undoing Changes & Removing Files

1
git diff [--staged]
Shows unstaged line-by-line differences (working tree vs. index) or staged differences (--staged: index vs. HEAD).
git diff git diff --staged
2
git restore [--staged] <file>
Undoes uncommitted changes in the working tree or unstages a file from the index.
git restore app.cs discards unstaged local edits; git restore --staged app.cs unstages the file while keeping your local edits.
git restore app.cs git restore --staged app.cs
3
git reset [--soft|--mixed|--hard] <rev>
Moves HEAD to a target commit and resets the staging index and/or working tree depending on the flag.
--soft keeps changes staged; --mixed (default) keeps edits unstaged; --hard permanently discards uncommitted changes in both index and working tree.
git reset --soft HEAD~1 git reset --mixed HEAD~1 git reset --hard HEAD~1
4
git rm <file>
Removes a tracked file from the working tree and stages the deletion in the index for the next commit.
git rm obsolete.txt

Lesson 4: Agile Mindset, Manifesto, Principles & MVP

01
Agile Umbrella

Agile vs. Scrum & The Agile Umbrella

Core Distinction
Agile is a broad umbrella of software development approaches focused on the final product and customer value, whereas Scrum is one specific framework under that umbrella.
1
Why Today’s Projects Need Agile
Modern projects require close collaboration across different departments and backgrounds with a common understanding of the project’s goal.
Without continuous communication and shared alignment, what the customer wanted, what was designed, and what was built end up completely mismatched.
2
Scrum
The most popular lightweight Agile framework, built around short time-boxed iterations (Sprints), defined roles, events, and artifacts.
Plans, builds, and delivers small, potentially shippable product increments every 2 to 4 weeks.
3
Kanban
A visual workflow method that uses a board with columns and Work-In-Progress (WIP) limits.
Focuses on continuous flow and removing bottlenecks without requiring fixed-length Sprints.
4
Extreme Programming (XP)
An engineering-focused Agile method emphasizing pair programming, Test-Driven Development (TDD), and continuous integration.
Improves software quality and responsiveness to changing customer requirements through strict technical practices.
5
Feature Driven Development (FDD)
An iterative approach that organizes project work around designing and building specific client-valued features.
Breaks domain models into small feature lists that can each be implemented in no more than two weeks.
6
Adaptive Software Development (ASD), Crystal Clear & RUP
Additional iterative approaches under the Agile umbrella.
ASD cycles through Speculate, Collaborate, Learn; Crystal Clear prioritizes people and communication in small teams; Rational Unified Process (RUP) structures iterative development into four phases.
02
Benefits & Delivery Model

Advantages of Agile, Incremental vs. Iterative & Success Factors

Five Advantages of Agile Approaches
1
Value- or Product-Orientation
Requirements are prioritized based on added value for the company and product.
Teams always build the highest-value features first while respecting technical dependencies.
2
Reduced “Time to Market”
Produces potentially shippable deliverables (increments) early on.
Eliminates risky “big bang” releases and gets working features into users’ hands faster.
3
Reduced Risk
Early review loops and stakeholder feedback prevent major flaws in the overall development process.
Ensures customer requirements are continuously verified rather than discovered too late.
4
High Quality
Early, well-established testing procedures and review loops allow early identification of bugs and issues.
Quality is built into every iteration instead of being tacked on at the end.
5
More Flexibility
Short development cycles (iterations) allow early adaptation and change without disrupting the overall process.
Teams can pivot smoothly when market conditions or customer priorities shift.
Incremental vs. Iterative Development

Iterative Approach

1
Continuous Refinement
Focuses on continuous improvement of existing features across repeated cycles.
Like sketching a rough outline first and refining the quality and detail in each pass.
+

Incremental Approach

2
Piece-by-Piece Addition
Focuses on adding new features to the overall product step by step.
Scrum combines both: refining existing features (iterative) while adding new features (incremental).
Key Factors That Make Agile Projects Successful
1
People & Culture
Teamwork, Open Communication, Trust and Respect, and an Open Approach to Mistakes.
2
Planning & Scope
Precise Requirements, “Real” Business Value, Reliable Planning, and Realistic Expectations and Project Goals.
3
Execution & Delivery
Flexibility, Great Tool Support, and Proper Handover of Project Results.
03
Values & Principles

The Agile Manifesto & Core Agile Principles

The 4 Core Value Statements of the Agile Manifesto
1
Individuals and Interactions over Processes and Tools
Software is developed by people; human interaction comes first.
Processes and tools are important, but should always support—rather than replace—direct communication.
2
Working Software over Comprehensive Documentation
Real business value comes from working product increments (deliverables and results).
Functional software is always more important than exhaustive theoretical planning documents.
3
Customer Collaboration over Contract Negotiation
Honest, close collaboration with the client enables rapid adaptation to changing demands.
Continuous partnership with the customer matters more than rigid, pre-negotiated contracts.
4
Responding to Change over Following a Plan
Plans must acknowledge uncertainty and leave space for changes.
Adapting to complex requirements and shifting market environments is prioritized over blindly following an outdated plan.
Key Agile Principles Pursued by Agile Teams
1
Customer Satisfaction
Our highest priority is to satisfy the customer through early and continuous delivery of valuable software.
2
Continuous Delivery
Deliver working software frequently, from a couple of weeks to a couple of months, with a preference to the shorter timescale.
3
Working Software
Working software is the primary measure of progress.
4
Sustainable Development
Agile processes promote sustainable development; sponsors, developers, and users should be able to maintain a constant pace indefinitely.
5
Support Motivated Individuals
Build projects around motivated individuals; give them the environment and support they need, and trust them to get the job done.
6
“Face-to-Face” Communication
The most efficient and effective method of conveying information to and within a development team is face-to-face conversation.
04
Product Strategy & Values

Minimum Viable Product (MVP) & The 5 Scrum Values

Minimum Viable Product (MVP)
“The Minimum Viable Product (MVP) is that version of a new product which allows a team to collect the maximum amount of validated learning about customers with the least effort.”

MVP Benefit & Correct Progression

1
Benefit of an MVP
Gain an understanding of client expectations without wasting excessive time on development.
Build usable stages (skateboard → scooter → bicycle → motorcycle → car) rather than unusable isolated parts (one wheel → axle → chassis).
VS

Common MVP Pitfall

2
Pitfall of an MVP
Teams put too much focus on “minimal” instead of “viable” and sacrifice quality.
An MVP must still be functional, reliable, and valuable enough for real customers to use.
The 5 Core Scrum Values
1
Respect
Mutual respect is the foundation for open and constructive collaboration.
Team members value each other’s skills, perspectives, and contributions.
2
Focus
Scrum executes in short cycles (Sprints) with clear, specific goals that require undivided attention.
Sprint Goals can only be achieved when the team focuses on current Sprint work without multitasking distractions.
3
Courage
Team members need courage to think out of the box and follow new approaches despite risk and uncertainty.
Empowers the team to speak up about blockers, challenge assumptions, and innovate.
4
Openness
The Scrum Team and stakeholders communicate in an open and honest way about progress, risks, changes, and problems.
Transparency ensures issues are surfaced early so the team can adapt together.
5
Commitment
The Scrum Team is intrinsically motivated and committed to the product, Sprint Goals, and mutual agreements.
Every member dedicates their best effort to achieving the team’s shared objective.

Lesson 5: Scrum Framework, User Stories, Velocity & Burndown

01
3 Scrum Roles

Scrum Structure (3-3-5) & The 3 Scrum Roles

Scrum at a Glance (3-3-5 Structure)
Scrum consists of 3 Roles, 3 Artifacts, and 5 Official Events executing in short Sprints (2–4 weeks). Agile teams have no hierarchies—all three roles collaborate closely.
1. Product Owner
1
Customer Representative
A single person working as the “voice of the customer”.
2
Vision & Business Value
Responsible for the overall product vision, economic success, and maximizing business value.
3
Backlog Ownership
Maintains and prioritizes the Product Backlog and negotiates Sprint Goals.
4
Story Acceptance
Approves or rejects finished User Stories within each Sprint.
2. Scrum Master
1
Process Guardian
Responsible for the Scrum process—ensuring everyone follows Scrum rules and guidelines.
2
Team Enablement
Creates an environment where the team works self-organized and cross-functionally.
3
Impediment Removal
Removes impediments (blockers), risks, and external distractions.
4
Facilitation & Coaching
Moderates communication between PO and Dev Team (often an objective external coach).
3. Development Team
1
Team Size (5 to 9 Members)
Typically 5 to 9 people responsible for building and testing the working product.
2
Cross-Functional Skills
Cross-functional (developers, testers, business analysts, domain experts in one team).
3
Self-Organized Execution
Self-organized and autonomous on how to achieve agreed Sprint Goals.
4
Co-Located Collaboration
Ideally located in a single room to support direct face-to-face collaboration.
02
3 Artifacts & Quality Gates

Scrum Artifacts, Definition of Ready (DoR) & Definition of Done (DoD)

The 3 Official Scrum Artifacts
1
Product Backlog
The prioritized master list of all desired requirements for the product, owned and ranked by the Product Owner.
It is dynamic (new requirements can be added and priorities changed) and visible to all stakeholders and the Scrum Team.
2
Sprint Backlog
The subset of Product Backlog items selected as the work list for the current Sprint.
Referenced daily during the Daily Scrum and tracked via the Sprint Burndown Chart.
3
Product Increment
The sum of all Product Backlog items completed during the current Sprint and all previous Sprints that are potentially shippable.
Every Increment must be a working, tested, documented, and usable product that is additive to all prior increments.
Definition of Ready (DoR) vs. Definition of Done (DoD)

Definition of Ready (DoR)

1
Pre-Development Quality Gate
General criteria a User Story must satisfy before development starts (before entering the Sprint Backlog).
Established by PO and Dev Team, known to all members, and displayed publicly to prevent mid-Sprint confusion and wasted time.
2
Example DoR Criteria
Understood by all parties (with sketches/notes); meets INVEST criteria; has clear Acceptance Criteria; is estimated and prioritized; fits in one Sprint; no blocking external dependencies or open questions.
VS

Definition of Done (DoD)

1
Post-Development Quality Gate
General checklist of criteria a requirement must meet to be considered complete and accepted.
Helps the Scrum Team know what quality work is required and helps the Product Owner decide whether a story is accepted or refused at Sprint Review.
2
DoR & DoD vs. Acceptance Criteria
DoR and DoD apply generally to all User Stories, whereas Acceptance Criteria apply to one specific User Story.
03
5 Events + Refinement

Scrum Events & Scaling Scrum

0
Product Backlog Refinement (Ongoing Activity, Not an Official Event)
Review, clarify, and prioritize Product Backlog items before Sprint Planning so stories meet the Definition of Ready.
Time-Box: ~10% of Dev Team’s capacity • Participants: Agile Team + Stakeholders.
1
Sprint
Time-boxed development period (usually 2 or 4 weeks) in which product increments are planned, designed, built, and tested; contains all other Scrum events.
Time-Box: 2 or 4 weeks • Participants: Entire Scrum Team.
2
Sprint Planning
Product Owner presents highest-priority backlog items and the Sprint Goal; the team selects items for the Sprint Backlog and breaks stories into Tasks.
Time-Box: ~2 hours per Sprint week • Participants: Entire Scrum Team.
3
Daily Scrum
A 15-minute daily stand-up to inspect progress and identify impediments by answering: What did you do yesterday? What will you do today? Are there any impediments?
Time-Box: 15 minutes daily • Participants: Agile Team (Product Owner optional).
4
Sprint Review
Held at the end of a Sprint to demonstrate the Product Increment, gather stakeholder feedback, and verify whether the Definition of Done is met.
Time-Box: ~1 hour per Sprint week • Participants: Agile Team + Stakeholders.
5
Sprint Retrospective
The final meeting of the Sprint where the team reflects on its own collaboration and process, shares lessons learned, and defines improvements for the next Sprint.
Time-Box: ~1 hour per Sprint week (max 3 hours for a 4-week Sprint) • Participants: Agile Team only (closed to outsiders).
Scrum for Big Projects (Scaling Scrum)
1
One Shared Product Backlog & Shared Definition of Done
Multiple Scrum Teams build one product together, each running its own Sprints and Daily Scrums.
Product Owners hold integration meetings across Sprint Backlogs so all teams meet a shared Definition of Done.
2
Scrum of Scrums (Global Stand-Up)
Cross-team coordination meeting attended by all Scrum Masters (and Product Owners).
Sometimes supported by additional team members to resolve cross-team dependencies and integration issues.

Requirements Hierarchy, Epics vs. User Stories & INVEST

4-Level Requirements Hierarchy in Scrum (Broadest to Smallest)
04 — Theme
A group of Epics that follow a specific strategic goal to describe products or projects.
03 — Epic
Roughly described large functionality spanning multiple Sprints; must be broken down into User Stories.
02 — User Story
Specific description of a single feature/functionality that must be delivered within a single Sprint.
01 — Task
Operative, concrete actions (programming steps, meetings, quality checks) required to deliver a User Story.

1

2

New/unfamiliar to the Dev Team, who have had no time to raise questions yet.
3
Risk
Includes severe risks whose consequences are not yet evaluated.
4
Size
Too big for a single Sprint; spans multiple Sprints and must be split into User Stories.

User Story Format, Acceptance Criteria & Template Fields
1
Standard User Story Format
Title + “As a <role>, I want to <functionality>, so that <business value/benefit>”.
Describes WHAT the user can do and WHY, never HOW to program it (the Dev Team decides the technical “how” in Sprint Planning).
2
Acceptance Criteria
Explicit, testable, and traceable conditions defined before development starts that must be met for a specific User Story to be considered “Done”.
Example for Create User Accounts: Administrator can enter username and email, system automatically generates an initial password, and system emails the password to the user.
3
User-Story Template Sections
Title, Requestor (for clarification), Estimation, ID, Involved Parties/Systems, Description (As / I want to / So that), Acceptance Criteria, Sketch/Screenshot, Business Value/Consequences (for PO prioritization), and Dependencies/Risks.

Planning & Monitoring

Velocity, Capacity Calculations & Burndown Charts

1. Velocity Rules & Calculation
1
Definition of Velocity
The running average of all successfully completed Story Points over the last 3 Sprints.
First reliable Velocity calculation is possible after 3 completed Sprints; Velocity stabilizes after a few initial Sprints.
2
Do Not Count Unfinished Work at All
Only User Stories that are 100% finished (“Done”) count toward Velocity.
Example: If Story A (13 pts, 100%), Story B (8 pts, 100%), Story C (1 pt, 100%), and Story D (13 pts, 95%) are worked on, Story D counts as 0, giving a Sprint Velocity of 13 + 8 + 1 = 22 Story Points.
3
3-Sprint Running Average Example
If Sprint 4 = 22 pts, Sprint 5 = 25 pts, and Sprint 6 = 27 pts, then Velocity = (22 + 25 + 27) / 3 = ~25 Story Points.
4
Velocity “No-Go’s”
Never calculate the Velocity of individual people (only the team matters), and never use Velocity to calculate bonuses (which causes inflated Story Point estimates).
2. Standard Capacity vs. Available Sprint Capacity
1
Capacity Definition
The Development Team’s actual time available (in hours) for implementing User Stories after deducting Scrum Events, emails, trainings, and vacations.
Typically, 25% of an 8-hour workday is deducted for meetings and non-Story tasks, leaving 6 productive hours/day.
2
Standard Capacity Example
6 developers × 10 Sprint days = 60 person-days. At 6 productive hrs/day (8 hrs − 25%), Standard Capacity = 60 × 6 = 360 hours.
3
Available Sprint Capacity Example
If 1 developer is on vacation (−10 days) and the remaining 5 attend a 1-day training (−5 days), the team loses 15 days (90 hrs): Sprint Capacity = (60 − 15) × 6 = 270 hours, so Available Capacity = 270 / 360 = 75%.
3. Burndown Charts (Ideal Trend vs. Real Progress)
1
Axes of a Burndown Chart
The Y-Axis shows remaining Story Points for the current Sprint; the X-Axis shows the number of Sprint days.
2
Ideal Trend Line
A straight diagonal line dividing total planned Story Points (e.g., 20) by total Sprint days (e.g., 10) for rough orientation.
3
Real Progress Line
Updated daily from Sprint Backlog updates showing Story Points completed (“Done”).
Often shows little progress in the very first days of a Sprint because it naturally takes several days to complete a full User Story.
