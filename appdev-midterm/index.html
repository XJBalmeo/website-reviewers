Application Development and Emerging Technologies

Lesson 1: SDLC, Modern Architecture, MVC & DevOps

01
Lifecycle Phases

Software Development Life Cycle (SDLC) Phases

Core Concept: The Software Development Life Cycle (SDLC) is a shared map of how a product moves from an initial idea to running software.
1
Planning: Define the goal, constraints, people, and success criteria before writing code. Establishes project scope, timelines, resources, and feasibility at the very start.
2
Analysis: Gather and clarify requirements: what the system must do and for whom. Translates user and business needs into clear functional and non-functional specifications.
3
Design: Choose architecture, data models, interfaces, and how system parts will collaborate. Produces technical blueprints, database schemas, and UI wireframes before implementation begins.
4
Implementation: Build working software from the design, in small verifiable pieces when possible. Developers write, compile, and integrate the actual source code for the application.
5
Testing: Check that the product meets requirements and is safe to release. Verifies functionality, performance, and security while catching defects before users see them.
6
Deployment: Release the application to users in a controlled, repeatable way. Packages and publishes the validated build to production servers or app stores.
7
Maintenance: Fix defects, adapt to change, and keep the system healthy after launch. Covers ongoing bug patches, performance tuning, security updates, and new feature enhancements.
02
Lifecycle Models

Comparing SDLC Models: Waterfall, Agile & Spiral

1. Waterfall
A
When to Use: Requirements are stable, the domain is well understood, and a linear plan is realistic. Best for fixed-scope projects with predictable rules.
B
Waterfall Flow: Phases run once, in order. Each phase finishes completely before the next starts; change late in the project is expensive.
2. Agile
A
When to Use: You need working software often and expect requirements to evolve. Ideal for fast-moving products where customer needs change over time.
B
Agile Flow: Phases repeat in short cycles. Short cycles repeat analysis, design, build, and test, while user feedback steers the next increment.
3. Spiral
A
When to Use: Larger, riskier efforts where prototypes and risk reviews drive each cycle. Used when technical or safety risks must be evaluated before committing to full builds.
B
Spiral Flow: Risk-driven iterative loops. Each loop plans, assesses risk, builds a prototype or increment, and evaluates before the next loop.
03
Application Architecture

Modern Applications & Client-Server Layers

Core Architecture: A modern web application is a client that talks to a server over HTTP. The server owns business rules and data, while the client owns the user experience.
Three-Tier Layer Explorer
1
Client Layer: The browser or front-end app users interact with directly (such as an Angular or React web app). It renders screens, collects user inputs or answers, and calls backend APIs over HTTP.
2
Server Layer: The backend application and API (such as an ASP.NET Core Web API) that processes requests. It enforces business rules, validates inputs, handles security/authentication, and communicates with the database.
3
Database Layer: The persistent data storage system (such as SQL Server) that stores and retrieves records. It keeps application entities, user accounts, and transactions safe and organized on disk.
Modern Application Concepts
1
SPA (Single-Page Application): The client stays loaded in the browser and updates the page without a full reload. Only the needed data is fetched in the background, making navigation feel instant and fluid.
2
API (Application Programming Interface): JSON over HTTP lets many different clients (web, mobile, desktop) share one server. The backend exposes clean endpoints that any authorized front-end device can call.
3
Separation of Concerns: UI, business rules, and data storage are kept in separate layers rather than mixed into one file. This modular structure makes code easier to read, test, debug, and maintain over time.
04
Architectural Pattern

Model-View-Controller (MVC) Architecture

Purpose of MVC: MVC separates data (Model), presentation (View), and request handling (Controller) so each part can change with less chaos.
1. Model
M
Data and Rules: Represents domain entities, business logic, and data state (e.g., users, questions, orders). Defines what data the application holds and how it is stored in the database.
2. View
V
Presentation / UI: The visual interface shown to the user (screens, forms, buttons, templates). Displays data from the system and captures user actions like clicking Submit.
3. Controller
C
Request Handler: Receives a request, uses models, and returns a result. Acts as the traffic coordinator between incoming HTTP requests and backend Models.
How an MVC Request Flows End-to-End
1
Step 1 (View): The user interacts with the View (e.g., clicking a Submit button in the front-end app).
2
Step 2 (Controller): The Controller receives the HTTP request (such as POST /api/submit) and invokes the appropriate business logic.
3
Step 3 (Model & Database): The Model is validated and saved in the database (such as SQL Server), and a response is returned.
05
CI/CD & Automation

DevOps and the 5-Stage CI/CD Pipeline

What is DevOps? A way of working where development and operations share one path from code change to production, with fast feedback and minimal manual effort.
The 5 Steps of a CI/CD Pipeline
1
Commit: A developer records a change in version control (Git). Pushing that commit automatically triggers the start of the CI/CD pipeline.
2
Build: Automation compiles the backend API and front-end app so everyone uses the exact same recipe. Catches missing dependencies or compilation errors immediately on a clean build server.
3
Test: Automated checks catch regressions before a person has to click through every screen manually. Runs unit, integration, and end-to-end tests automatically on every build.
4
Deploy: Automation releases the verified build to staging or production environments in a repeatable way. Eliminates risky manual file copying and ensures consistent, fast software delivery.
5
Monitor: Logs, system health, and user feedback flow back so the next commit is better informed. Tracks live performance, uptime, and error rates in production to guide future improvements.
Key DevOps Automation Practices
1
Continuous Integration (CI): Every commit is built and tested automatically when pushed to the shared repository. Prevents "integration hell" by catching broken code or failing tests within minutes.
2
Infrastructure as Code (IaC): Servers and environments are described in versioned files, not manual "tribal knowledge". Allows teams to spin up identical test and production servers automatically from code scripts.
3
Feedback Loops: Test results, live monitoring, and user metrics inform the team’s very next change. Continuous telemetry connects daily engineering decisions directly to real-world system behavior.

Lesson 2: C# Programming & .NET Fundamentals

01
Language & Runtime

Introduction to C#, .NET & Compilation

1
What is C#? A modern, object-oriented and type-safe (statically typed) programming language from Microsoft. Object-oriented means modeling data and behavior with classes; type-safe means the compiler checks data types (like int count = 3;) before the program runs.
2
.NET and Tools: C# source files end in .cs and target the .NET platform. Edited and debugged using Visual Studio or Visual Studio Code, and managed from the terminal with the dotnet CLI.
3
Compilation vs. Runtime: Compile (Build) translates .cs files into intermediate language; Run (Runtime) executes the built program. If your code has a syntax error (such as a missing semicolon ;), compilation fails and the program never starts executing.
.NET CLI Commands & Hello World Styles
# Create, enter, and run a new C# console project via dotnet CLI dotnet new console -n HelloLab cd HelloLab dotnet run
// Style 1: Modern Top-Level Statements (Program.cs) Console.WriteLine("Hello, World!"); // Style 2: Classic Program Class with Main Entry Point class Program { static void Main() { Console.WriteLine("Hello, World!"); } }
02
Data & Expressions

Data Types, Variables, Constants & Operators

1
int & double (Numeric Types): int stores whole numbers (e.g., 18), while double stores decimal numbers (e.g., 3.5). Remember that dividing two int values truncates the decimal part; use double when you need decimals.
2
string & bool (Text & Logic Types): string holds text in double quotes (e.g., "Alex"); bool holds true or false. Every condition inside an if or while statement must evaluate to a bool.
3
const (Constants): Declares a fixed value that cannot change after you set it (e.g., const int MaxScore = 100;). Attempting to reassign a constant later in the code causes a compile-time error.
4
Arithmetic Operators: +, -, *, /, and % (modulo/remainder). The modulo operator % returns the remainder of division (e.g., 10 % 2 == 0 prints True because 10 is even).
5
Comparison & Logical Operators: Comparison (==, !=, <, >, <=, >=) and Logical (&& AND, || OR, ! NOT). && requires both conditions to be true, || requires at least one to be true, and ! flips true/false.
int age = 18; double gpa = 3.5; string name = "Alex"; bool isEnrolled = true; const int MaxScore = 100; int n = 10; Console.WriteLine(n % 2 == 0); // Prints True (remainder of 10 / 2 is 0)
03
Control Flow & Methods

Decisions (if / else), Loops & Methods

1
if / else if / else Statements: Evaluates a bool condition in parentheses and runs only the first matching branch. Allows programs to make decisions such as checking whether a student’s grade passes or needs a retry.
2
for Loop vs. while Loop: Use a for loop when you know the count in advance; use a while loop to repeat while a condition stays true. Both loops repeat a block of statements enclosed in curly braces { } until their condition becomes false.
3
Methods and Local Scope: A method is a named reusable block of code with parameters and a return type. Variables declared inside a method have local scope—they exist only inside that method and are invisible outside it.
// 1. Decision: if / else if / else int grade = 80; if (grade >= 90) { Console.WriteLine("A"); } else if (grade >= 75) { Console.WriteLine("B"); // Runs when grade is 80 } else { Console.WriteLine("Keep practicing"); } // 2. Loops: for (known count) vs. while (condition-based) for (int i = 0; i < 5; i++) { Console.WriteLine(i); } int count = 3; while (count > 0) { count--; } // 3. Reusable Method with parameters and return value int Add(int a, int b) { return a + b; }
04
Syntax Rules

Basic Syntax: Delimiters, Comments, Keywords & Naming

1
Statements & Semicolons (;): Most C# statements (declarations, assignments, method calls) end with a semicolon ;. Omitting a required semicolon at the end of a statement causes a compile error.
2
Braces { }, Parentheses ( ) & Square Brackets [ ]: { } group statements into a block; ( ) hold conditions or arguments; [ ] index arrays. Each pair of symbols has a distinct grammatical role in C# syntax.
3
Comments & Reserved Keywords: Use // for single-line comments and /* ... */ for multi-line comments. Reserved keywords (such as int, class, return, and if) have special meaning to the compiler and cannot be used as variable names.
4
Naming Conventions (camelCase vs. PascalCase): Use camelCase for local variables and parameters (itemCount); use PascalCase for methods, classes, and properties (CalculateTotal). Always choose descriptive names that explain what a value represents, not just its data type.
05
Console Apps & Collections

Basic Applications: Console I/O, Parsing & Arrays

1
Console Input & Number Parsing: Console.ReadLine() reads user input as text (string?); convert it with int.Parse or int.TryParse when you need a number. String interpolation ($"Hello, {name}") cleanly embeds variable values directly inside output strings.
2
Integer Division Truncation: Dividing two integers (int / int) discards any decimal remainder. Cast or declare values as double when your calculation requires a decimal result.
3
Arrays vs. List<T>: An array (int[]) holds a fixed number of values of the same type with zero-based indexing (starts at 0), whereas a List<int> can grow dynamically. Use scores[0] to access the first element and scores.Length to get the total number of items in the array.
// 1. Console I/O and String Interpolation Console.Write("Enter your name: "); string? name = Console.ReadLine(); Console.WriteLine($"Hello, {name}"); // 2. Zero-Indexed Array and .Length Property int[] scores = { 88, 91, 74 }; Console.WriteLine(scores[0]); // Prints 88 (first item is at index 0) Console.WriteLine(scores.Length); // Prints 3 (total items in array)

Lesson 3: Git Version Control & Repository Commands

01
Git Architecture

The Four Core Git Areas

How Git Tracks Changes: Files move from your Working Tree → into the Staging Area (Index) via git add → into the HEAD Snapshot (Commit Graph) via git commit.
1
Working Tree (Working Directory): Your active project folder where you create, edit, or delete files before staging them. Changes made here are unstaged (or untracked for brand-new files) until you run git add.
2
Staging Area (Index): The middle preparation zone that holds changes queued for the next commit. Lets you carefully select which modified files to group together into a single clean snapshot.
3
HEAD Snapshot: A pointer to the latest committed snapshot on your currently active branch. Whenever you create a new commit or switch branches, HEAD updates to point to that current state.
4
Commit Graph: The historical chain of parent-to-child commit snapshots across all branches in the repository. Allows teams to inspect project history, branch off safely, and merge features back together.
02
Basic Snapshot Workflow

Repository Setup, Staging & History Commands

1
git init: Creates a new Git repository in the current folder. HEAD points at main with no commits yet.
2
git status: Shows the current branch, staged changes, unstaged edits, and untracked files. The most frequently used inspection command to see what state your working tree and index are in.
3
git add <file> | git add .: Copies working-tree files into the index (staging area). Use git add readme.txt to stage a single file, or git add . to stage all modified and new files.
4
git commit -m "message": Records a permanent snapshot of the index and moves the current branch forward. Always write a clear, concise commit message describing what changed and why.
5
git log [--oneline]: Walks parent commits starting backward from HEAD. Passing --oneline prints a compact one-line summary (commit hash + message) for each commit.
# Initialize a repository, stage a file, commit it, and view history git init git status git add readme.txt git commit -m "Add initial readme file" git log --oneline
03
Branching & Merging

Branching, Switching & Merging Commands

1
git branch [name]: Lists existing branches (when run with no arguments) or creates a new branch pointing at HEAD. Note that git branch feature-login creates the branch pointer but keeps you on your current branch until you switch.
2
git switch [-c] <branch>: Moves HEAD to a target branch and updates the working tree. Adding the -c flag (git switch -c feature-login) creates a new branch and switches to it in one step.
3
git checkout [-b] <branch>: Older command for switching or creating branches. Running git checkout -b feature-login creates and switches to a new branch, just like git switch -c.
4
git merge <branch>: Joins another branch into the current branch (via fast-forward or 3-way merge). First switch to the receiving branch (e.g., git switch main), then run git merge feature-login.
# Create and switch to a feature branch, commit work, and merge into main git switch -c feature-ui git add . git commit -m "Add header layout" git switch main git merge feature-ui
04
Diffs, Undo & Removal

Inspecting Differences, Undoing Changes & Removing Files

1
git diff [--staged]: Shows unstaged differences (working tree vs. index) or staged differences (--staged: index vs. HEAD). Lets you review exact line-by-line additions and deletions before staging or committing.
2
git restore [--staged] <file>: Undoes uncommitted changes in the working tree or index. git restore app.cs discards unstaged edits in the file; git restore --staged app.cs unstages the file from the index without losing your edits.
3
git reset [--soft|--mixed|--hard] <rev>: Moves HEAD to a target commit and optionally resets the index and working tree. --soft moves HEAD only (keeps changes staged); --mixed (default) unstages changes; --hard discards changes in both the index and working tree.
4
git rm <file>: Removes a tracked file from the working tree and stages the deletion in the index. On the next commit, the file will no longer exist in the current branch snapshot.
# Inspect changes, unstage a file, discard edits, or remove a tracked file git diff # Compare working tree vs. staging index git diff --staged # Compare staging index vs. HEAD commit git restore --staged a.cs # Unstage a.cs back to working tree git restore a.cs # Discard unstaged local edits in a.cs git reset --soft HEAD~1 # Undo last commit but keep its changes staged git rm obsolete.txt # Delete tracked file and stage the deletion

Lesson 4: Agile Mindset, Manifesto, Principles & MVP

01
Agile Umbrella

Agile vs. Scrum & The Agile Umbrella

Core Distinction: Agile is a broad umbrella of software development approaches focused on the final product and customer value, whereas Scrum is one specific framework under that umbrella.
1
Why Today’s Projects Need Agile: Modern projects require close collaboration across different departments and backgrounds with a common understanding of the project’s goal. Without continuous communication and shared alignment, what the customer wanted, what was designed, and what was built end up completely mismatched.
2
Scrum: The most popular lightweight Agile framework, built around short time-boxed iterations (Sprints), defined roles, events, and artifacts. Plans, builds, and delivers small, potentially shippable product increments every 2 to 4 weeks.
3
Kanban: A visual workflow method that uses a board with columns and Work-In-Progress (WIP) limits. Focuses on continuous flow and removing bottlenecks without requiring fixed-length Sprints.
4
Extreme Programming (XP): An engineering-focused Agile method emphasizing pair programming, Test-Driven Development (TDD), and continuous integration. Improves software quality and responsiveness to changing customer requirements through strict technical practices.
5
Feature Driven Development (FDD): An iterative approach that organizes project work around designing and building specific client-valued features. Breaks domain models into small feature lists that can each be implemented in no more than two weeks.
6
Adaptive Software Development (ASD), Crystal Clear & RUP: Additional iterative approaches under the Agile umbrella. ASD cycles through Speculate, Collaborate, Learn; Crystal Clear prioritizes people and communication in small teams; Rational Unified Process (RUP) structures iterative development into four phases.
02
Benefits & Delivery Model

Advantages of Agile, Incremental vs. Iterative & Success Factors

Five Advantages of Agile Approaches
1
Value- or Product-Orientation: Requirements are prioritized based on added value for the company and product. Teams always build the highest-value features first while respecting technical dependencies.
2
Reduced “Time to Market”: Produces potentially shippable deliverables (increments) early on. Eliminates risky “big bang” releases and gets working features into users’ hands faster.
3
Reduced Risk: Early review loops and stakeholder feedback prevent major flaws in the overall development process. Ensures customer requirements are continuously verified rather than discovered too late.
4
High Quality: Early, well-established testing procedures and review loops allow early identification of bugs and issues. Quality is built into every iteration instead of being tacked on at the end.
5
More Flexibility: Short development cycles (iterations) allow early adaptation and change without disrupting the overall process. Teams can pivot smoothly when market conditions or customer priorities shift.
Incremental vs. Iterative Development

Iterative Approach

1
Continuous Refinement: Focuses on continuous improvement of existing features across repeated cycles. Like sketching a rough outline first and refining the quality and detail in each pass.
+

Incremental Approach

2
Piece-by-Piece Addition: Focuses on adding new features to the overall product step by step. Scrum combines both: refining existing features (iterative) while adding new features (incremental).
Key Factors That Make Agile Projects Successful
1
People & Culture: Teamwork, Open Communication, Trust and Respect, and an Open Approach to Mistakes.
2
Planning & Scope: Precise Requirements, “Real” Business Value, Reliable Planning, and Realistic Expectations and Project Goals.
3
Execution & Delivery: Flexibility, Great Tool Support, and Proper Handover of Project Results.
03
Values & Principles

The Agile Manifesto & Core Agile Principles

The 4 Core Value Statements of the Agile Manifesto
1
Individuals and Interactions over Processes and Tools: Software is developed by people. Processes and tools are important, but should always support—rather than replace—human interaction.
2
Working Software (Deliverables, Results) over Comprehensive Documentation: Real business value comes from working product increments. Functional software is always more important than exhaustive theoretical planning documents.
3
Customer Collaboration over Contract Negotiation: Honest, close collaboration with the client enables rapid adaptation to changing demands. Continuous partnership with the customer matters more than rigid, pre-negotiated contracts.
4
Responding to Change over Following a Plan: Plans must acknowledge uncertainty and leave space for changes. Adapting to complex requirements and shifting market environments is prioritized over blindly following an outdated plan.
Key Agile Principles Pursued by Agile Teams
1
Customer Satisfaction: Our highest priority is to satisfy the customer through early and continuous delivery of valuable software.
2
Continuous Delivery: Deliver working software frequently, from a couple of weeks to a couple of months, with a preference to the shorter timescale.
3
Working Software: Working software is the primary measure of progress.
4
Sustainable Development: Agile processes promote sustainable development; sponsors, developers, and users should be able to maintain a constant pace indefinitely.
5
Support Motivated Individuals: Build projects around motivated individuals; give them the environment and support they need, and trust them to get the job done.
6
“Face-to-Face” Communication: The most efficient and effective method of conveying information to and within a development team is face-to-face conversation.
04
Product Strategy & Values

Minimum Viable Product (MVP) & The 5 Scrum Values

MVP Definition: “The Minimum Viable Product (MVP) is that version of a new product which allows a team to collect the maximum amount of validated learning about customers with the least effort.”

MVP Benefit & Correct Progression

1
Benefit: Gain an understanding of client expectations without wasting excessive time on development. Build usable stages (skateboard → scooter → bicycle → motorcycle → car) rather than unusable isolated parts (one wheel → axle → chassis).
VS

Common MVP Pitfall

2
Pitfall: Teams put too much focus on “minimal” instead of “viable” and sacrifice quality. An MVP must still be functional, reliable, and valuable enough for real customers to use.
The 5 Core Scrum Values
1
Respect: Mutual respect is the foundation for open and constructive collaboration. Team members value each other’s skills, perspectives, and contributions.
2
Focus: Scrum executes in short cycles (Sprints) with clear, specific goals that require undivided attention. Sprint Goals can only be achieved when the team focuses on current Sprint work without multitasking distractions.
3
Courage: Team members need courage to think out of the box and follow new approaches despite risk and uncertainty. Empowers the team to speak up about blockers, challenge assumptions, and innovate.
4
Openness: The Scrum Team and stakeholders communicate in an open and honest way about progress, risks, changes, and problems. Transparency ensures issues are surfaced early so the team can adapt together.
5
Commitment: The Scrum Team is intrinsically motivated and committed to the product, Sprint Goals, and mutual agreements. Every member dedicates their best effort to achieving the team’s shared objective.

Lesson 5: Scrum Framework, User Stories, Velocity & Burndown

01
3 Scrum Roles

Scrum Structure (3-3-5) & The 3 Scrum Roles

Scrum at a Glance: Scrum consists of 3 Roles, 3 Artifacts, and 5 Official Events executing in short Sprints (2–4 weeks). Agile teams have no hierarchies—all three roles collaborate closely.
1. Product Owner
1
Single person working as the “voice of the customer”.
2
Responsible for the overall product vision, economic success, and maximizing business value.
3
Maintains and prioritizes the Product Backlog and negotiates Sprint Goals.
4
Approves or rejects finished User Stories within each Sprint.
2. Scrum Master
1
Responsible for the Scrum process—ensuring everyone follows Scrum rules and guidelines.
2
Creates an environment where the team works self-organized and cross-functionally.
3
Removes impediments (blockers), risks, and external distractions.
4
Moderates communication between PO and Dev Team (often an objective external coach).
3. Development Team
1
Typically 5 to 9 people responsible for building and testing the working product.
2
Cross-functional (developers, testers, business analysts, domain experts in one team).
3
Self-organized and autonomous on how to achieve agreed Sprint Goals.
4
Ideally located in a single room to support direct face-to-face collaboration.
02
3 Artifacts & Quality Gates

Scrum Artifacts, Definition of Ready (DoR) & Definition of Done (DoD)

The 3 Official Scrum Artifacts
1
Product Backlog: The prioritized master list of all desired requirements for the product, owned and ranked by the Product Owner. It is dynamic (new requirements can be added and priorities changed) and visible to all stakeholders and the Scrum Team.
2
Sprint Backlog: The subset of Product Backlog items selected as the work list for the current Sprint. Referenced daily during the Daily Scrum and tracked via the Sprint Burndown Chart.
3
Product Increment: The sum of all Product Backlog items completed during the current Sprint and all previous Sprints that are potentially shippable. Every Increment must be a working, tested, documented, and usable product that is additive to all prior increments.
Definition of Ready (DoR) vs. Definition of Done (DoD)

Definition of Ready (DoR)

1
Pre-Development Quality Gate: General criteria a User Story must satisfy before development starts (before entering the Sprint Backlog). Established by PO and Dev Team, known to all members, and displayed publicly to prevent mid-Sprint confusion and wasted time.
2
Example DoR Criteria: Understood by all parties (with sketches/notes); meets INVEST criteria; has clear Acceptance Criteria; is estimated and prioritized; fits in one Sprint; no blocking external dependencies or open questions.
VS

Definition of Done (DoD)

1
Post-Development Quality Gate: General checklist of criteria a requirement must meet to be considered complete and accepted. Helps the Scrum Team know what quality work is required and helps the Product Owner decide whether a story is accepted or refused at Sprint Review.
2
DoR vs. Acceptance Criteria: DoR & DoD apply generally to all User Stories, whereas Acceptance Criteria apply to one specific User Story.
03
5 Events + Refinement

Scrum Events & Scaling Scrum

Event / Activity Time-Box / Duration Participants Purpose & Key Activities
0. Product Backlog Refinement
(Ongoing activity, not an official event)		 ~10% of Dev Team’s capacity Agile Team + Stakeholders Review, clarify, and prioritize Product Backlog items before Sprint Planning so stories meet the Definition of Ready.
1. Sprint Usually 2 or 4 weeks Scrum Team Time-boxed development period in which product increments are planned, designed, built, and tested; contains all other Scrum events.
2. Sprint Planning ~2 hrs per Sprint week Scrum Team PO presents highest-priority backlog items and Sprint Goal; team selects items for the Sprint Backlog and breaks stories into Tasks.
3. Daily Scrum 15 minutes daily Agile Team (PO optional) Inspect progress and identify impediments by answering 3 questions: (1) What did you do yesterday? (2) What will you do today? (3) Are there any impediments?
4. Sprint Review ~1 hr per Sprint week Agile Team + Stakeholders Held at the end of a Sprint to demonstrate the Product Increment, gather stakeholder feedback, and verify if the Definition of Done is met.
5. Sprint Retrospective ~1 hr per Sprint week (max 3 hrs for 4 wks) Agile Team only (closed to outsiders) Last meeting of the Sprint where the team reflects on its own process, shares lessons learned, and defines improvements for the next Sprint.
Scrum for Big Projects (Scaling Scrum)
1
One Shared Product Backlog & Shared Definition of Done: Multiple Scrum Teams build one product together, each running its own Sprints and Daily Scrums. Product Owners hold integration meetings across Sprint Backlogs so all teams meet a shared Definition of Done.
2
Scrum of Scrums (Global Stand-Up): Cross-team coordination meeting attended by all Scrum Masters (and Product Owners). Sometimes supported by additional team members to resolve cross-team dependencies and integration issues.
04
Requirements & User Stories

Requirements Hierarchy, Epics vs. User Stories & INVEST

4-Level Requirements Hierarchy in Scrum (Broadest to Smallest)
04 — Theme: A group of Epics that follow a specific strategic goal to describe products or projects.
03 — Epic: Roughly described large functionality spanning multiple Sprints; must be broken down into User Stories.
02 — User Story: Specific description of a single feature/functionality that must be delivered within a single Sprint.
01 — Task: Operative, concrete actions (programming steps, meetings, quality checks) required to deliver a User Story.

How Epics Differ from User Stories

1
Complexity: Too complex or unclear for immediate development; needs clarification.
2
Unknown: New/unfamiliar to the Dev Team, who have had no time to raise questions yet.
3
Risk: Includes severe risks whose consequences are not yet evaluated.
4
Size: Too big for a single Sprint; spans multiple Sprints and must be split into User Stories.
VS

User Story “INVEST” Rule

I
Independent: Fairly independent from other User Stories.
N
Negotiable: Reminders for conversation discussed between PO and Dev Team.
V
Valuable: Delivers specific business value to the user.
E
Estimated: Effort/Story Points have been estimated.
S
Sized appropriately: Small enough to finish within one Sprint.
T
Testable: Clearly testable with defined test cases.
User Story Format, Acceptance Criteria & Template Fields
1
Standard User Story Format: Title + “As a <role>, I want to <functionality>, so that <business value/benefit>”. Describes WHAT the user can do and WHY, never HOW to program it (the Dev Team decides the technical “how” in Sprint Planning).
2
Acceptance Criteria: Explicit, testable, and traceable conditions defined before development starts that must be met for a specific User Story to be considered “Done”. Example for Create User Accounts: Administrator can enter username and email, system automatically generates an initial password, and system emails the password to the user.
3
User-Story Template Sections: Title, Requestor (for clarification), Estimation, ID, Involved Parties/Systems, Description (As / I want to / So that), Acceptance Criteria, Sketch/Screenshot, Business Value/Consequences (for PO prioritization), and Dependencies/Risks.
05
Planning & Monitoring

Velocity, Capacity Calculations & Burndown Charts

1. Velocity Rules & Calculation
1
Definition of Velocity: The running average of all successfully completed Story Points over the last 3 Sprints. First reliable Velocity calculation is possible after 3 completed Sprints; Velocity stabilizes after a few initial Sprints.
2
Do Not Count Unfinished Work at All: Only User Stories that are 100% finished (“Done”) count toward Velocity. Example: If Story A (13 pts, 100%), Story B (8 pts, 100%), Story C (1 pt, 100%), and Story D (13 pts, 95%) are worked on, Story D counts as 0, giving a Sprint Velocity of 13 + 8 + 1 = 22 Story Points.
3
3-Sprint Running Average Example: If Sprint 4 = 22 pts, Sprint 5 = 25 pts, and Sprint 6 = 27 pts, then Velocity = (22 + 25 + 27) / 3 = ~25 Story Points.
4
Velocity “No-Go’s”: Never calculate the Velocity of individual people (only the team matters), and never use Velocity to calculate bonuses (which causes inflated Story Point estimates).
2. Standard Capacity vs. Available Sprint Capacity
1
Capacity Definition: The Development Team’s actual time available (in hours) for implementing User Stories after deducting Scrum Events, emails, trainings, and vacations. Typically, 25% of an 8-hour workday is deducted for meetings and non-Story tasks, leaving 6 productive hours/day.
2
Standard Capacity Example: 6 developers × 10 Sprint days = 60 person-days. At 6 productive hrs/day (8 hrs − 25%), Standard Capacity = 60 × 6 = 360 hours.
3
Available Sprint Capacity Example: If 1 developer is on vacation (−10 days) and the remaining 5 attend a 1-day training (−5 days), the team loses 15 days (90 hrs): Sprint Capacity = (60 − 15) × 6 = 270 hours, so Available Capacity = 270 / 360 = 75%.
3. Burndown Charts (Ideal Trend vs. Real Progress)
1
Axes of a Burndown Chart: The Y-Axis shows remaining Story Points for the current Sprint; the X-Axis shows the number of Sprint days.
2
Ideal Trend Line: A straight diagonal line dividing total planned Story Points (e.g., 20) by total Sprint days (e.g., 10) for rough orientation.
3
Real Progress Line: Updated daily from Sprint Backlog updates showing Story Points completed (“Done”). Often shows little progress in the very first days of a Sprint because it naturally takes several days to complete a full User Story.
